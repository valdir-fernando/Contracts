# Minha conta: dados e senha independentes

O formulário de dados mantém `PUT /account` e o botão **Salvar**, sem campos de senha. A operação não altera a senha, mesmo quando `password` e `password_confirmation` são enviados diretamente. A senha atual não é exigida para salvar os dados; clientes anteriores que ainda enviem `current_password` continuam tendo esse valor validado. Permissões, proteção do último administrador, versão, locks e auditoria dos dados foram preservados.

Após uma linha separadora, o formulário **Alterar senha** envia exclusivamente a senha atual, nova senha, confirmação e versão para `PUT /account/password` (`account.password`). O endpoint exige autenticação e conta ativa, limita tentativas, valida a senha atual e exige nova senha de pelo menos 12 caracteres com letras e números. Dentro da transação, bloqueia e revalida o ator, versão e senha atual; atualiza o hash, incrementa `session_version`, limpa `remember_token` e registra `own_password_changed`, sem registrar senhas ou hashes. Mantém a sessão atual e invalida as outras pelo mecanismo existente de versão. Campos de identidade/permissão enviados a esse endpoint não são persistidos.

Os testes verificam formulários separados, salvamento de dados sem senha, impossibilidade de alterar senha pelo botão Salvar, senha atual incorreta, confirmação inválida, senha fraca, versão inválida/desatualizada, preservação dos dados e de outras contas, auditoria e invalidação de sessões antigas. Nenhuma migration ou alteração de dados reais é necessária.

Validação executada no Docker: testes direcionados de conta/segurança (44 testes, 337 asserções); `composer check:architecture` (3 testes, 4 asserções); `composer test:unit` (81 testes, 195 asserções); `composer check` (Pint aprovado; 746 testes, 7436 asserções, 1 ignorado); `composer check:static` (sem erros); `npm run build` (aprovado). `git diff --check` passou. Testes de banco usam SQLite isolado; não foi realizada inspeção visual manual no navegador.
